# Project Workflow

This workflow is mandatory for agents working in this repository.

## Existing Issues

When instructed to work on an existing project issue, update the selected issue's Linear status before performing any constituent task. The status must reflect that the issue is in progress.

After the status is updated, begin the task and continue until it is complete. Do not stop to ask for confirmation or guidance unless an important decision must be made and the issue content does not provide enough direction to make the decision safely.

## New Work

When instructed to work on a task that is not explicitly identifiable as an existing project issue, create a new Linear issue before beginning implementation. Use metadata and properties appropriate to the task and scope of work.

If the user indicated that work should begin immediately, update the new issue's status to reflect that it is in progress before starting. If the user only asked for issue creation, create the issue, then stop and ask whether it should be worked.

## Verification

After changing code or project files, run all applicable formatters, linters, type-checkers, and tests. If any verification step fails, fix the failures before proceeding.

Use the repository's existing tooling and conventions. When a tool is not yet established, use the closest standard tool for the language or file type and document any verification gap in the final report.

When a change affects the stable JSON contract, explicitly evaluate whether the JSON schema version should change. This includes changes to envelope fields, command-specific `data` fields, structured warnings or errors, redaction indicators, profile/environment metadata, or documented JSON semantics. If a bump is needed, recommend it clearly and follow the release metadata update path in `docs/release.md`.

## Commits

Once all changes pass verification, group related changes together and commit them with a concise, multi-line conventional commit message.

Always include related issue IDs in the subject line when one or more related issues exist.

## Tracker Updates

After committing, update related issue statuses and labels to reflect the current state. Account for whether human review or additional verification is still needed. Usually this means setting the issue status to `In Review` and the triage label to `ready-for-human`.

Add a comment to each related issue with a link to the specific commit containing the related changes. If multiple commits are created for an issue, include one commit link per line.

The Linear MCP tool for creating or updating comments is `save_comment`. It creates or updates a comment on a Linear issue, project, initiative, document, or project milestone. If `id` is provided, it updates the existing comment; otherwise it creates a new one. To start a new thread, pass `body` and exactly one of `issueId`, `projectId`, `initiativeId`, `documentId`, or `milestoneId`. Comments on issues, projects, and initiatives become top-level discussion threads. Comments on documents and milestones become description comments. To reply to an existing thread, pass `parentId` and `body`; the reply inherits the parent's thread type, so no entity reference is needed.

Every Linear comment posted during triage or workflow updates must begin with:

```markdown
> *This was generated by AI during triage.*
```

Once the above steps have been completed, advise your human partner with concise step-by-step instructions on how the task results/output can be manually verified, including exact commands and/or tests to run (if applicable). Post these instructions in a comment on the relevant issue under a top-level heading of "MANUAL TESTING INSTRUCTIONS".

## Remote Pushes

Never push to a remote unless explicitly instructed.

This prevents messy revert or rollback work on the remote and keeps review workflow clean.
